Spawn a teammate agent as part of the current team.
The teammate runs as a child session with its own agent type, prompt, and permissions.
The spawn call returns immediately with a started handle and does not block the lead: the teammate runs in the background. Continue useful decomposition, integration, review, or decision work. When no useful work remains, finish the current response normally. The runtime parks successful finalization while finite teammates remain active.
The teammate receives team context and its final result is posted back to the lead automatically as a team message.
Teammates are instructed to send proactive kickoff, progress, handoff, and blocker updates through the team mailbox.
Do not sleep, repeatedly read team state, ask for routine updates, or send filler. Teammates must send material progress, blockers, questions, and results without a lead status request. Relevant teammate or user events wake the lead.
The lead receives automatic started/waiting updates, and active dependency teammates are notified when someone is waiting on their work.
Use this when you need multiple agents working in parallel on different aspects of the team's goal.
Use this aggressively for independent research, file reading, implementation slices, reviews, and verification so the lead session can preserve context and focus on coordination.
For review phases, spawn fresh read-only reviewer sessions inside the same active team rather than creating a second team or resuming a finished teammate.
Prefer several focused teammates over one broad teammate when the work can proceed in parallel.
Spawn multiple independent teammates in one parallel tool-call batch whenever possible.
Use depends_on or wait_for when this teammate must wait for one or more teammate names/session IDs to complete before starting.
Use lifecycle="daemon" only for long-lived monitoring, sentinel, rolling-checklist, or similar assignments. lifecycle defaults to "task" for finite work.
Daemon spawn returns after initialization, not after team shutdown. A daemon remains registered and usually becomes idle between mailbox-driven work cycles.
Do not use daemon teammates for ordinary finite research, implementation, review, or verification tasks.
For risky or broad edits, set plan_mode so the teammate must submit a plan for lead approval before implementation.
Use variant only with an exact available variant key shown in the team lead prompt for the teammate's effective model. Omit variant for default behavior or when variant names are uncertain.
Use lower reasoning-effort variants only for simple, well-scoped work with precise instructions. Use default or medium variants for bounded implementation, moderate debugging, and verification that requires judgment. Use default or the highest appropriate variant for ambiguous root-cause analysis, architecture decisions, security-sensitive changes, broad refactors, and adversarial review.
Keep model and variant choices out of role_prompt; the lead owns variant selection through this tool.
Before implementation starts on multi-step team work, make sure shared tasks have owners; use team_task_create dependencies when one task needs another result.

After teammate results return, check team_get_messages ONCE for any pending handoff or blocker messages before deciding the next coordination step. You will be automatically woken when teammates send you messages — DO NOT poll team_get_messages in a loop.

CRITICAL: As the lead, your role is to delegate and coordinate. Do NOT duplicate active teammate tasks. You cannot predict what work teammates will produce, and duplicating their effort wastes resources and creates conflicts. Integrate results when they arrive. As results arrive, continuously think about what new sub-tasks can be split off and delegated — decomposition is an ongoing process, not a one-time step.
